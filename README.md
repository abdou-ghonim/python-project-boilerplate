# Python Project Boilerplate

Flask API + React/Vite/Tailwind SPA, with the database and the authentication
method chosen by configuration rather than by rewriting code.

```
DB_PROVIDER=sqlite|postgresql|mysql|mssql      AUTH_PROVIDER=local|oidc|none
```

Everything else — logging, rate limiting, caching, background jobs, the Docker
build — is the same whichever pair you pick.

## Quick start

```bash
cp .env.example .env            # then set SECRET_KEY (setup.sh does it for you)
scripts/setup.sh                # venv, dependencies, .env, schema, admin, demo data
scripts/dev.sh                  # API on :5000, Vite on :5173
```

Sign in with `DEFAULT_ADMIN_USERNAME` / `DEFAULT_ADMIN_PASSWORD` from `.env`.

## Layout

```
app/
  __init__.py          create_app(): startup checks, wiring, request lifecycle
  routes.py            /health and the SPA catch-all
  api/                 HTTP only — parse, delegate to a service, serialise
  database.py          sqlite · postgresql · mysql · mssql, in one file
  redis.py             the connection, caching, rate limiting, locks
  logging_setup.py     rotating files, JSON option, the request id
  errors.py            every API failure as JSON
  sql_scripts.py       the .sql runner behind `flask db-apply`
  auth/                local · oidc · none, plus the JWT and the revocation list
  models/
    user.py            the account, mapped onto YOUR user table by config
    models.py          GENERATED by `flask generate-models`
    extended_models.py anything you hand-write
  services/            business logic — the demo domain, and background jobs
sql/<provider>/        THE SCHEMA — plain .sql, applied by `flask db-apply`
cli/                   flask commands (db-apply, generate-models, jobs, users…)
lib/sql_code_generate/ vendored sqlacodegen fork behind `flask generate-models`
frontend/              React 19 + Vite + Tailwind v4 + TypeScript
scripts/               setup · dev · test · rename-project · docker-deploy
logs/                  rotating app.log and error.log
```

## Configuration

All of it lives in `config.py`, read from the environment (`.env` in
development). `.env.example` documents every variable. The settings that decide
whether the app is *safe* to run are checked at startup and are fatal:

| Check | Why it is fatal |
|---|---|
| `SECRET_KEY` unset, placeholder, or under 32 bytes | A guessable key lets anyone forge an admin JWT |
| Database connection not encrypted (outside development) | Every query and every row would cross the network in clear text |
| `REDIS_REQUIRED` and Redis unreachable | Rate limiting and token revocation would silently stop working |
| `CORS_ORIGINS=*` outside development | A wildcard origin with credentials is never what was intended |
| `AUTH_PROVIDER=none` outside development | Every request would be treated as an admin |

## Database providers

Set `DB_PROVIDER` and the discrete `DB_*` parts; the provider builds the URI,
tunes the engine and checks the transport. `SQLALCHEMY_DATABASE_URI` overrides
all of it when a managed-database connection string will not decompose.

| Provider | Driver | Install | Transport check |
|---|---|---|---|
| `sqlite` | stdlib | — | n/a (warns outside development) |
| `postgresql` | psycopg 3 | `requirements/postgresql.txt` | `sslmode=require`/`verify-full` |
| `mysql` | PyMySQL | `requirements/mysql.txt` | an `ssl_*` parameter must be present |
| `mssql` | pyodbc + MS ODBC 18 | `requirements/mssql.txt` | `Encrypt=yes` |

## Schema

The project is **database first**. The schema is SQL, under `sql/<provider>/`,
and the Python models are derived from it:

```bash
flask db-apply          # sql/<provider>/*.sql  ->  database
flask generate-models   # database              ->  app/models/models.py
```

`db-apply` runs the dialect's scripts in filename order. It keeps no record of
what it has already run, so every statement is written to be safe to re-run and
applying the directory again is a no-op — that is what makes it usable both to
create a database and to bring one up to date. Versioning, rollback and an
audit of what ran where are a migration tool's job (Alembic, Flyway,
`sqlpackage`); this is deliberately the smaller thing.

`generate-models` reflects the live database through the vendored generator and
rewrites `app/models/models.py` in full, so nothing hand-written survives there.
Hand-written models go in `app/models/extended_models.py`, and tables mapped
there are skipped during reflection so they do not appear twice.

There is no `create_all()` anywhere in the normal path. `flask db-init` is the
code-first direction kept for one case — standing an already-reflected schema up
in an empty database — and it refuses to run until `generate-models` has written
`models.py`.

`sql/README.md` covers adding a script, the statement splitter and `GO` batches.
`tests/test_schema_sql.py` checks the SQLite DDL against the ORM models, and the
test suite builds its own schema from those same files.

## Auth providers

| Provider | How you sign in | Notes |
|---|---|---|
| `local` | username + password against your user table | scrypt hashes, per-IP and per-account lockout, `flask create-user` |
| `oidc` | redirect to an IdP, back to `/api/auth/callback` | Entra ID, Google, Keycloak, Okta; roles from a configurable claim |
| `none` | nothing | development only; refuses to start elsewhere |

All three issue the same JWT, so `@require_auth`, `@require_role("manager")` and
the frontend are unchanged by the choice. `GET /api/auth/config` tells the SPA
which login UI to render. Roles are ranked (`user` < `manager` < `admin`), so a
guard admits every role above it.

Logout revokes the token's `jti` in Redis until it expires; `flask set-role`
revokes every session for a user, since their claims are now stale.

### Pointing auth at a table you already have

The account model is not a table this project insists on creating. It maps onto
whatever is already there:

```bash
AUTH_USER_TABLE=Users
AUTH_USER_SCHEMA=security
AUTH_USER_COLUMNS=username=Email,display_name=FullName,role=,last_login_at=
```

An entry with nothing after the `=` says the table has no such column. The
attribute becomes a constant instead — `role=` means everyone reads as
`AUTH_DEFAULT_ROLE` — so the rest of the code, which only ever says
`user.role`, carries on working and no query asks for a column that is not
there. `username`, the primary key and (for local logins) the password hash are
the three that cannot be dropped that way.

The JSON the API returns is keyed on the attribute, not the column, so renaming
`username` to `Email` does not rename the field the frontend reads. Roles
themselves are configurable too: `AUTH_ROLES=viewer,editor,owner`.

The whole mapping is `app/models/user.py`, and it is about thirty lines of
table before any logic. SSO additionally needs `external_id` and
`auth_provider` columns, since it matches on the IdP's subject claim.

## Redis

One connection pool, five uses, all namespaced by `REDIS_KEY_PREFIX`:

- rate limiting (`@rate_limit("10/minute")`) — shared across workers
- token revocation — what makes logout mean something
- caching (`@cached("items", ttl=60)`) with namespace invalidation
- OIDC login state, so the callback works on any worker
- distributed locks (`with redis_lock("nightly-sync"):`)

Background jobs use a second, undecoded connection, because RQ stores pickled
payloads. Enqueue with `enqueue(func, …)` and run `flask jobs worker`.

Without Redis each of these degrades in-process and says so. That is fine in
development; `REDIS_REQUIRED=true` (the default elsewhere) makes it a boot
failure instead.

## Logging

`logs/app.log` and `logs/error.log`, rotating at `LOG_MAX_BYTES` with
`LOG_BACKUP_COUNT` kept, plus stdout. `LOG_FORMAT=json` emits one object per
line for a log shipper. Every line carries a request id, which is also returned
as `X-Request-ID` and included in API error responses — one id ties a user's
report to the traceback.

## Commands

```bash
flask db-check          # what am I connected to, and does it answer?
flask db-apply          # run sql/<provider>/*.sql, seed the default admin
flask db-apply --dry-run
flask generate-models   # reflect the database into app/models/models.py
flask db-init           # code-first fallback; needs models.py to exist first
flask create-user       # add a local account
flask list-users
flask set-role alice admin
flask seed-demo --count 25
flask cache-clear items
flask jobs worker|status|demo
flask routes            # Flask's own; this project adds no command of that name
```

## Tests

```bash
scripts/test.sh         # pytest + frontend type-check
```

The suite runs against SQLite in a temporary file and uses Redis when one is
reachable, under a per-run key prefix.

## Docker

```bash
docker compose up --build                       # app + worker + Redis
DB_PROVIDER=postgresql docker compose --profile postgresql up --build
scripts/docker-deploy.sh 1.0.0                  # build and push
```

The database driver is a build argument, so an image is built for the provider
it will run against — only the `mssql` build pulls in the ~150 MB Microsoft ODBC
layer. The image builds the SPA in a Node stage, compiles Python wheels in a
second, and runs as a non-root user with a healthcheck on `/health`, which
answers 503 when the database (or a required Redis) is unreachable.

## Dropping what you do not need

Every optional piece has a switch that makes it a no-op, so you can turn it off,
check nothing broke, and only then delete the code:

| Setting | Turns off | Then you can delete |
|---|---|---|
| `REDIS_ENABLED=false` | every Redis-backed feature at once; nothing connects | `app/redis.py` — the connection, caching, rate limiting and locks are all in it |
| `RATE_LIMIT_ENABLED=false` | per-IP limits and the login lockout | the rate-limiting section of `app/redis.py` |
| `CACHE_ENABLED=false` | `@cached` — the functions still run | the caching section of `app/redis.py` |
| `JOBS_ENABLED=false` | `enqueue()`, which then refuses with a clear message | `app/services/jobs.py`, `cli/jobs.py`, the worker in `docker-compose.yml` |

Turning Redis off also disables `AUTH_PROVIDER=oidc`, which needs somewhere to
keep login state between the redirect and the callback, and it makes logout
local to one worker — `REDIS_REQUIRED` exists to stop that happening by
accident rather than on purpose.

`Item` in `app/models/extended_models.py`, the `item` table in each
`sql/*/001_core.sql`, `app/services/item_service.py`, `app/api/items.py`,
